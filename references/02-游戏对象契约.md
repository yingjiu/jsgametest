# 02 · 游戏对象契约 `window.__DUAL_GAME__`

游戏对象是**唯一**要交给平台的入口。注册方式（任选其一）：

```js
window.__DUAL_GAME__ = G;          // 推荐（早期脚本也能用）
// 或
DualArena.registerGame(G);         // 等价
```

平台在页面加载完成后：注入 SDK → 调 `DualArena.boot()` → 读 `Arena.getInit()` → 依次调你的钩子。

---

## 1. 钩子一览

| # | 钩子 | 调用端 | 调用时机 | 作用 |
|:--:|---|---|---|---|
| 1 | `init(ctx)` | 两端 | boot 后一次 | 建初始状态、存 `ctx` |
| 2 | `onStart(ctx)` | 两端 | **倒计时闸门**打开那一下 | 正式开跑前的收尾（可选） |
| 3 | `tick(dt)` | **仅房主** | 每帧（闸门开后） | 推进权威逻辑 |
| 4 | `onInput(seat,x,y,a,id)` | **仅房主** | 有输入事件时 | 处理某座位的一次触摸 |
| 5 | `serialize()` → 任意/JSON 串 | **仅房主** | ~30Hz | 产出权威状态 |
| 6 | `applyState(obj)` | **仅客人** | 收到状态时 | 用权威状态更新本地 |
| 7 | `render(now,ctx,c)` | 两端 | 每帧 | 自绘到 canvas |
| 8 | `hud()` → `{hp,scores,tip}` | 两端 | 每帧 | 原生 HUD 数据（可选） |
| 9 | `isFinished()` → bool | 两端 | 每帧 | 是否结束 |
| 10 | `result()` → `{winner,scores,summary,stats}` | 两端 | 结束时一次 | 结算数据 |

补充说明：

- **`state()`**：`serialize` 的别名（二选一，SDK 优先用 `serialize`）。
- **`crossScreen`**：建议在游戏对象上也写一份（与 manifest 一致），方便预览页读取；平台以 manifest 为准。
- 钩子里抛异常不会崩 App，会被 SDK 捕获并打到 `logcat`（`tag=duizhan`，前缀 `frame err:` / `init err:`）。

---

## 2. 生命周期时序

```
页面加载完成
   │  平台注入 dual-arena-sdk.js，调用 DualArena.boot()
   ▼
读取 Arena.getInit()  ──►  ctx 建立（见 03）
   ▼
init(ctx)                              ← 建初始状态（此时还没开跑）
   ▼
Arena.onReady()                        ← 平台知道页面就绪
   ▼
…平台播「准备 / 1 / 开始！」倒计时…      ← 期间 Arena.isStarted() === false
   │                                      SDK 不会调 tick/onInput，也不判结算
   ▼
Arena.isStarted() === true  →  onStart(ctx)
   ▼
每帧循环：
   ├─ 房主：pollInputs() → onInput(...)  →  tick(dt) / tick(固定步长)  →  serialize() → Arena.onState()
   └─ 客人：pollRemoteState() → applyState(obj)
   ├─ render(now, ctx, c)                （两端都跑）
   ├─ hud() → Arena.onHud(json)
   └─ isFinished() && result() → Arena.onOver(json)   （只上报一次）
   ▼
平台显示结算浮层 → 房主点「再来一局」→ 对本游戏是一次**全新 boot**（重新 init）
```

> 「再来一局」不是复用你的对象状态，而是重新 `boot()`；**不要**依赖跨局的全局残留状态。

---

## 3. 帧循环细节（与兼容性有关）

- 帧循环由 `requestAnimationFrame` 驱动，`dt` 已夹紧到 `≤120ms`（防长时间卡顿后一次推进太多）。
- 声明了 `clock` cap 时，`tick` 以**固定步长** `1000/60 ms` 调用，最多一次补 5 步（逻辑与帧率解耦）；
  未声明 `clock` 时 `tick(dt)` 为**可变步长**。
- `serialize()` 的返回值可为**对象**（平台自行 `JSON.stringify`）或**已序列化的字符串**。
  - 若声明了 `ev` cap 且有未发送事件，平台会把它包成 `{"__v":2,"s":<状态>,"e":<事件>}`，客人端由 SDK 自动拆包（你无需处理）。
- 房主端 `onState` 回传被**节流到 ~30Hz**（渲染仍是 60Hz），所以快照体积很关键（见 `07`）。

## 4. 输入钩子的参数

```js
onInput: function (seat, x, y, a, id) { … }
```

| 参数 | 含义 |
|---|---|
| `seat` | 事件来自哪个座位（`0` 或 `1`），**不是**"本机座位" |
| `x, y` | **世界坐标**（已由平台换算好，见 `03`） |
| `a` | 动作码：`0`=按下 `1`=抬起 `2`=移动 `3`=取消 |
| `id` | 指针 id（多指时区分"哪根手指"） |

**建议**：判定类玩法只处理 `a === 0`；拖动类（拉弓/划线）才处理 `1/2/3`。
平台**不会**帮你过滤 MOVE 事件——不判 `a` 就会产生大量重复触发。

> 输入到达房主的顺序 = 判定顺序（先到先判、先到先得分）。房主自己的输入本地即时生效（少一个 RTT）。
